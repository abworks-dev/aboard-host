# Aboard Host Constitution

## Core Principles

### I. 单一事实所有者与稳定身份

- **INV-01**：一个正式事实只能有一个当前写入 owner；禁止 Go Host 与旧 TS Host 同时写入同一工作区事实。
- **INV-02**：所有业务资源必须携带稳定 `workspaceId`；本地模式也必须使用稳定 `tenantId`、`principalId`。
- **INV-03**：资源归属与授权不得依赖全局“当前工作区”，每次操作必须确定当前主体和目标工作区。
- **INV-04**：路径、名称不是身份；目录移动不得重新生成身份。
- **INV-05**：复制目录不得直接产生相同身份的第二个可写实例；目录副本不复制凭据、机器授权或有效执行权。

理由：目录是长期业务实例的载体，不是身份授权本身；禁止双主与串区。
数据库拥有正式业务状态、版本、引用和历史；不可变对象拥有原始字节，数据库保存关联与摘要。
候选文件、生成投影、安装登记与客户端缓存都不得成为第二事实源。

### II. 检查无副作用，打开失败不补种

- **INV-06**：`inspect` 不得创建、修复、迁移、激活插件或发起 Provider 请求。
- **INV-07**：已有目录缺库、坏摘要、身份冲突、未来格式必须拒绝，不得补种默认数据或降级成“新工作区”。
- **INV-08**：锁文件或 PID 存在不证明独占；写者排他必须有真实跨进程证据，覆盖竞争、异常退出和释放。

显式 `create` 与 `inspect/open` 必须分离。创建中断的残留不能被重开逻辑当成成功实例自动修复。
目录格式、数据库 schema、公共 API 分别版本化；旧身份目录 v1 不得加业务表后继续假称兼容。
完整业务格式是否采用 `formatVersion=2` 必须在对应 plan/research 评估并用夹具证明。

### III. 提交、对象与候选协议必须诚实

- **INV-09**：保存确认前不得发布成功事件，也不得允许依赖该提交的执行。
- **INV-10**：保存结果未知不等于回滚，也不等于可安全重试；必须保留可调查关联信息和恢复边界。
- **INV-11**：外部候选必须绑定 `baseRevision/baseDigest`；陈旧候选不得自动覆盖新版本。
- **INV-12**：正式提交成功与视图生成失败必须分别报告；生成投影不得覆盖未提交候选。
- **INV-13**：对象被正式引用前，最终字节必须存在且摘要可验证。
- **INV-14**：不得承诺未经验证的跨文件、数据库与硬件断电原子性。

直接编辑文件只产生候选；必须经过预览、结构/依赖校验和显式 Apply 才生效。
数据库与对象不是两个可独立修改的主库；失败必须报告其真实提交阶段。

### IV. 生命周期、逻辑终态与物理收尾分离

- **INV-15**：取消、超时、逻辑终态不代表物理 IO、Worker、Provider 已结束。
- **INV-16**：关闭、移动、备份必须遵守实际排空和未知结果边界，不得靠超时后删除锁宣称安全。
- **INV-17**：客户端关闭、断线、取消订阅只影响连接或订阅；取消 Run 是独立授权操作。

工作区业务状态、目录打开/关闭状态、只读/可写访问模式必须分别建模。
Run 的逻辑状态、物理收尾和持久化状态必须分别可观察。
关闭 A 不得关闭 B 或取消 B 的任务；不能因目录关闭就谎报 Run 已停止或保存已回滚。

### V. 当前授权、秘密与安装级容量

- **INV-18**：历史、公开 DTO、旧审批、哈希都不授予当前执行权限；执行前必须重校验当前授权与依赖。
- **INV-19**：拆库不得复制并放大全局容量或预算；安装级 owner 负责全局执行、公平性与生命周期协调。
- **INV-20**：密钥不得进入浏览器 DTO、普通日志、事件、错误或默认备份。
- **INV-21**：目录、Trust、cwd、原生进程都不自动等于 OS 安全沙箱；不得宣称子进程已防住恶意原生代码。

本地可信连接也必须认证；客户端路由、请求体自报身份和目录权限不是 Host 授权证明。
执行器可以使用 Node/Python/原生工具，但不得成为第二授权者或业务数据库写入者。
日志必须结构化、脱敏、可关联；排障信息只记录必要上下文，不泄漏秘密。

### VI. 四层隔离及共享故障边界

1. **数据隔离**：各工作区拥有独立数据库及对象归属。查询、修改、事件订阅、产物访问必须检查当前主体与目标工作区；拒绝跨区资源引用越权。
2. **生命周期/故障隔离**：候选错误、资源错误、依赖缺失限于相应范围。A 数据库损坏使 A 拒绝打开/写入，不得无理由使 B 不可用。安装身份、全局授权或共享持久化结果未知时，可保守阻断相关全局操作，但必须说明影响范围和原因；不得为局部可用绕过共享安全不变量。
3. **执行/资源隔离**：高风险插件/任务按需使用受控执行进程；必须定义超时、输出上限、取消、排空及资源限制。一工作区执行进程崩溃不应自动终止其他区任务；必须维持安装总容量，并采用公平调度或每区占用限制防止长期独占。子进程不是安全沙箱。
4. **共享基础设施影响**：第一版共享 Host 进程；进程崩溃、内存耗尽、磁盘满、机器断电可影响多个工作区。不承诺任何故障都互不影响。逐工作区子进程仅为后续可选专项，须另行设计数据库持有者、锁、授权与恢复协议。

跨区默认无任意互访。未来协作必须经 Host 完成：
来源身份 → 来源策略 → 目标公开能力及授权 → 目标业务提交 owner → 受限结果/回执。
不得直接访问其他区数据库或任意目录；A 的调用许可不得继承 B 的全部权限。
不得传递原始凭据、活控制句柄或旧审批作为授权。双库写入不是天然原子事务。
后续功能必须定义部分成功、取消、超时、重复提交、去重与审计；不得先造无消费者消息总线。

### VII. 独立引擎、可换客户端与真实可用性

Host 必须不依赖 React、Next.js、Vue、Electron 才能启动。一个安装级 Host 可以打开多个工作区。
客户端通过公共协议展示、交互、声明式渲染，只拥有查询缓存和非业务界面状态；
不得直接访问数据库、密钥、插件实现或任意服务器文件系统。
Go 转发到旧 TS Host、让旧 Host 永久拥有全部事实，不是目标终态。

Studio 是普通建设客户端而非特权入口：需求 → Host 生成服务 → 声明式候选 → 检查 → 差异预览 →
用户确认 → Host 正式提交 → 客户端渲染。页面描述布局、组件、数据绑定和动作；
任意第三方 React/Vue 源码不得进入可信应用依赖图。
缺少真实数据接口、业务能力或 renderer 时必须明确 `unavailable`，不得用假数据/空操作伪称可用。
明确保存的 Build/Studio 成果必须绑定工作区正式版本，不能只留在聊天中；无需为每次生成重编译 Host。

## Architecture and Security Constraints

- 目标采用 **Go 模块化单体 + 端口适配器**，不是微服务。
- 安装级拥有安装身份/认证/账户设置、凭据/密钥、插件包准入与可信缓存、工作区目录登记、当前机器授权、全局协调。
- 工作区拥有稳定身份、正式资源/配置/版本、插件组成与依赖、业务数据/Build 成果、Session/Run/事件/审计、对象引用与候选基线。
- 技术方向：受支持且固定版本的 Go；标准库优先 HTTP 查询/命令、SSE 订阅；真实 SQLite 与版本化 SQL migration；JSON Schema/OpenAPI 跨语言契约；不可变对象与数据库摘要引用。
- SQLite 驱动、跨进程锁、凭据存储、发布方式必须技术验证后定案。不得把偏好写成事实。
- 不引入 Redis、通用消息中间件、Kubernetes、分布式事务框架或无消费者的通用插件基础设施。
- 首期只承诺经验证的 Windows 本地文件系统、单安装 Host、全新工作区与合成数据、独立后端；现有 React 后接。
- 网络盘/云同步、多 Host 协同写、旧库/凭据自动导入、未知副作用自动续跑、跨机自动继承权限、未经验证跨平台锁都不在默认支持范围。
- 目标目录与完整路线只在 [总体范围](<../../docs/scope.md>) 维护；能力观察与迁移证据只在 [迁移基线](<../../docs/migration-baseline.md>) 维护。

## Development Workflow and Quality Gates

Spec Kit 是规格、计划、任务的主要流程；不得并行建立竞争权威的另一套方法文档。
按 constitution → specify → clarify → **用户批准规格** → plan/research → tasks → analyze → implement 推进。
功能级当前授权与历史批准统一由 [001 授权记录](<../../specs/001-host-workspace-foundation/authorization.md>) 记录；本宪章不维护当前功能阶段上限，历史批准不等于技术或业务验收。
技能必须在 Agent 会话中调用，不得当成终端命令。默认不修改工具模板、脚本和技能。

- 需求规格写场景、行为、失败边界、可观察成功标准；实现取舍留给 plan/research。
- 状态必须区分 proposed、designed、implemented、partial、deferred、retired；设计文档与测试存在不等于运行验收，未执行设计不得写 accepted ADR。
- 必须覆盖真实 SQLite、第二进程锁竞争、异常退出/释放/重启、保存失败/结果未知、陈旧候选/并发提交、取消/物理排空/迟到交付、串区与越权负例；按对应功能归属阶段验收，不把后期功能假塞进首片。
- race 检测、编译、Mock 只能证明各自范围；空目录、内存 Map、接口定义、健康检查不构成真实保存/重开交付。
- 只读旧源码只能形成有界证据。dirty 工作树不能用 HEAD 单独固定；跨语言摘要/序列化/版本比较必须建立固定字节和行为夹具，跨仓契约只能有一个权威来源。
- 项目开发日志与诊断仅放 Git 忽略的 `.data/logs/`；工具环境、缓存、本机状态、秘密不得提交。

## Governance

本宪章依据用户明确约束建立初版治理基线；宪章本身不授予功能规格批准或业务实现权限。001 的批准记录只在[功能授权记录](<../../specs/001-host-workspace-foundation/authorization.md>)维护，未代表任何业务已实现。
宪章优先于下属设计；发现冲突必须停止相关实现并提交明确修订，不能以兼容回退静默违背不变量。
修订必须说明变化、理由、受影响规格/契约、兼容与证据影响，并取得用户批准。
删除/重定义原则或改变权威边界升 MAJOR；新增原则/实质扩展升 MINOR；不改语义的澄清升 PATCH。
每个 plan 必须逐项检查适用原则、标记豁免及批准证据；每次交付必须分清实际验证与未验证项。
真实数据的不可逆变更、旧项目修改、外部发布均需另外明确授权；本宪章不提供这些授权。

仓库最小持久规则和入口见 [AGENTS.md](<../../AGENTS.md>)。
